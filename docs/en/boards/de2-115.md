# DE2-115

## 1. Reference

The Terasic DE2-115 has a Cyclone IV E (`EP4CE115F29C7`) with 128 MB of SDRAM, 8 MB of NOR FLASH, 2 MB of SRAM and an RS-232 UART. The package is in `boards/de2-115/`. The package format is in [formato.md](formato.md) and the table of boards in [placas.md](placas.md).

## 2. Platforms

Two platforms run on this board, both with the console on the JTAG UART and the eight-digit display.

| Platform | Folder | FLASH | RAM | Use |
| :--- | :--- | :--- | :--- | :--- |
| `de2-115-n2` | `src/cyclone-iv-e/de2-115-n2/` | emulated in M9K blocks, 252 KiB | emulated in M9K blocks, 128 KiB | level N2, no memory chip of the board |
| `de2-115` | `src/cyclone-iv-e/de2-115/` | NOR chip, 1 MiB of the chip | SDRAM of two 16-bit chips, 128 MiB | level N4 |

The Quartus project of each one comes from `riscv-tools board generate`, and the `config.yaml` of the platform only says where it is and how the host reaches the memories.

## 3. NOR FLASH

The chip has an 8-bit bus, and a 32-bit word costs four reads. The `nor_flash_ctrl` controller runs on the core clock and counts the cycles of the chip timings with a pin margin of 5 ns. The SoC speaks in absolute addresses and the chip in offsets: the generated top subtracts the start of the FLASH region (`0x1000`) from the read and command addresses, so that offset 0 of the chip is `0x1000`. The chip sector is 64 KiB, which is why bank B starts at `0x81000` (offset `0x80000`). The FLASH region of the map covers 1024 KiB, the window of the region router.

The erase, program and protect commands arrive through the FLASH controller of the Peripherals (window `FLASH_CTRL`), which is the path of the program update.

## 4. SDRAM

The two 16-bit chips share control, address and `DRAM_CLK` and form a 32-bit bus with the mask `DRAM_DQM[3:0]`. The controller uses `dq_width` equal to 32, burst of 1 and 25 word address bits.

| Item | Value |
| :--- | :--- |
| Controller clock (`mem`) | 100 MHz |
| Address map | 128 MiB RAM at `0x40000000`, from `0x40000000` to `0x47FFFFFF` |
| Window of the cache tag | 128 MiB (`CACHE_WINDOW_BITS` equal to 27), derived from the RAM region by the generator |
| Debug port | reaches the $2^{25}$ words: bit 24 of the address travels in bit 3 of the operation code |

The map generator picks the smallest aligned window that holds the ROM and the RAM, and the cache tag keeps the address bits below it. The 128 MiB RAM needs the window of $2^{27}$ bytes, so the tag keeps the bits up to 26. The host words (`stdout`, `tohost` and `fromhost`) sit at the top of the RAM, at `0x47FFFBE0` and above.

## 5. Particulars

| Item | Treatment |
| :--- | :--- |
| IDCODE | `020F70DD`, the same as the 10CL120 and the EP3C120; `board scan` tells the board by its package |
| Reset | `KEY[0]`, active low, which is also a bit of the `keys` role |
| `SLEW_RATE` | the `cyclone-iv-e` family does not get the option, which Quartus refuses on 3.3-V LVTTL (error 169303) |
| Display | eight digits, `quartus.display_digits: 8` in `config.yaml` |
| Fetch clock | the platform does not declare `clocks.fetch`: the fetch clock is the core one, without the offset the DE0-CV uses |

## 6. NOR programmer

The NOR has no JTAG loader, and a chip of this kind only changes through the commands of the FLASH controller. The `rom_write_method: nor_program` of `config.yaml` writes bank A like this.

1. `compile` links `paths.nor_programmer` (`runtime/nor_programmer.c`) into the SDRAM and keeps its entry.
2. The host loads the programmer, the job (magic `NROP`, destination, size) and the image into the SDRAM through the debug port.
3. The host writes the RAM entry of the BOOT_MEMORY, magic `RAMB` and the entry of the programmer in the last 8 bytes of the RAM, and writes `fromhost`.
4. The core restarts, the BOOT_MEMORY clears the magic and jumps to the programmer, which erases and programs the bank through the FLASH controller, checks the readback and stops in `rv32_wait_restart` with `tohost` equal to 1.

The result on the board is in [resultados-de2-115.md](resultados-de2-115.md).

## 7. Expansion pins

The pins below are in `pins.yaml` with the `manual` seal and become available to an I/O role when the `board.yaml` schema accepts one. All are bidirectional and have no polarity, except the LEDs.

| Group | Signals | Pins | Manual table | Level |
| :--- | :--- | :--- | :--- | :--- |
| 40-pin header | `GPIO[35:0]` | 36 I/O, plus VCC5, VCC3P3 and two GND | 4-12 | JP6, factory 3.3 V |
| General-purpose connector | `EX_IO[6:0]` | 7 | 4-13 | 3.3 V |
| Green LEDs | `LEDG[8:0]` | 9 | 4-3 | 2.5 V |
| HSMC, clocks | `HSMC_CLKIN0`, `HSMC_CLKIN_[N\|P][2:1]`, `HSMC_CLKOUT0`, `HSMC_CLKOUT_[N\|P][2:1]` | 10 | 4-9 | JP7, factory 2.5 V (`HSMC_CLKIN0` follows JP6) |
| HSMC, data | `HSMC_D[3:0]`, `HSMC_RX_D_[N\|P][16:0]`, `HSMC_TX_D_[N\|P][16:0]` | 72 | 4-9 | JP7, factory 2.5 V |
| Extra clocks | `CLOCK2_50`, `CLOCK3_50`, `SMA_CLKIN`, `SMA_CLKOUT` | 4 | 4-5 | 3.3 V or JP6 |

The HSMC has 82 I/O pins, each usable as general-purpose I/O; those the manual calls LVDS are differential pairs that work as such only with the 100 ohm resistor at the receiver. The power (12 V and 3.3 V), the JTAG, `HSMC_SDA` and `HSMC_SCLK` are not I/O pins listed in table 4-9.
