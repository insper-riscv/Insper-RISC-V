# Generating the project of a board

## 1. Principle

Each concept has one generator, and the generator reads the data from the single source. No generated file is edited by hand, and no concept is generated by two paths.

| Concept | Single source | Output |
| :--- | :--- | :--- |
| Memory map | `platform.yaml` | VHDL package, linker scripts, `.specs` and headers (`generate-memory-map`) |
| Chip timing | `Memory/chips/<chip>.yaml` | VHDL package `chip_<chip>_pkg` and I/O delays of the `.sdc` |
| Pins | `board.yaml` and `pins.yaml` | Pin and I/O standard assignments of the `.qsf` |
| Clocks and PLL | `clocks` of the `platform.yaml`, `clocks` of the `board.yaml` and the family | PLL module (`altera_pll` or `altpll`) |
| Timing constraints | Clocks, chips and SoC domains | `.sdc` |
| Quartus project | Family, device and source closure of the `top` | `.qpf` and `.qsf` |
| Board top | All of the above | Thin entity |
| Fit estimate | Family calibration and `platform.yaml` | `capacity.json` |

## 2. The command

```bash
riscv-tools --root . --board <board> board generate --platform src/<family>/<platform>/platform.yaml --out build
```

The output folder is a build folder and is not versioned. The project lives in `build/<platform>-<board>/`.

| Generated file | Content |
| :--- | :--- |
| `<platform>_<board>_top.vhd` | Thin top (section 3) |
| `<platform>_<board>_pll.v` | Family PLL with the requested clocks |
| `<platform>_<board>.qpf` and `.qsf` | Family, device, sources, pins, I/O standards, optimization mode and seed |
| `<platform>_<board>.sdc` | Clocks, generated clocks, I/O delays and domain exceptions |
| `chip_<chip>_pkg.vhd` | Timing of each memory chip of the board |
| `capacity.json` | Estimate per resource and the result of the fit policy |

The memory map is written at the paths the `generate` field of the platform declares, by the same code as `generate-memory-map`.

| Option | Effect |
| :--- | :--- |
| `--board` (global) | Board; without it the `board` field or the only entry of `boards` applies |
| `--target` | Component whose source closure enters the `.qsf`; without it the `top` of the platform applies |
| `--seed` | Placement seed, default 5 |
| `--accept-inferred-pins` | Accepts building with an `inferred` pin |
| `--check` | Writes nothing; exits with status 1 if the project or the map on disk differ from what would be generated |

Warnings (optional role missing, memory pin clock phase not measured, backend without an entity) go to `stderr`. An invalid input exits with status 2, and a profile that exceeds 100 % of a resource refuses the generation.

## 3. The generated top

The top only connects. No logic is born in it besides the reset.

1. Board ports, generated from the `io` and `memories` roles of the `board.yaml` (18-bit `LEDR` and 32-bit `DRAM_DQ` on the `de2-115`).
2. The PLL and the reset: the user reset with the board polarity, and the SoC reset released two `core` cycles after the PLL locks.
3. The `soc` instance, with the clocks by role and the I/O vectors with normalized polarity.
4. One backend instance per external region (section 4).
5. The pin ring of the device backends, with one tri-state buffer per bit in a `generate`.
6. The Zihpm generics, the role polarities, the critical-path cuts and the FLASH controller of the program update, with the same values for every board that turns the feature on.

## 4. Backends the top instantiates

| Backend | Generated instance | Generics filled |
| :--- | :--- | :--- |
| `emulado` FLASH | FLASH chip, dual-port storage, loader and Virtual JTAG shell | Size, latency from `memory.rom.latency`, family |
| `emulado` RAM | RAM port over the memory block | Size, latency |
| `dispositivo/sdram` | Data and instruction bridges, arbiter, debug master, Virtual JTAG shell and controller | Width (16 or 32 bits), row, column and bank bits, chip timing, `mem` period |
| `dispositivo/nor` | 8-bit NOR FLASH controller with page read and commands | Random and page access cycles, sector size |

A region with `dispositivo/sram`, `flash-interna` or `serial` generates no instance: the top warns and leaves the region idle.

## 5. PLL and constraints per family

| Family | PLL primitive |
| :--- | :--- |
| Cyclone V, Cyclone V SoC | `altera_pll` |
| Cyclone IV E, MAX 10, Cyclone 10 LP | `altpll` |

The PLL generator picks the smallest VCO within the `vco_mhz` range of the family for which each output has an integer divider from 1 to 511 and the phase is a multiple of one eighth of the VCO period. Without a solution, or with more outputs than `outputs_max`, the error names the requests (V7 and V15). Changing the core frequency is generating the PLL again with another `clocks.core.mhz`.

The `.sdc` carries, in this order, the reference clock, `derive_pll_clocks`, the generated clock of the memory pin and the I/O delays of each chip, the memory read path, the crossings among `mem`, `core`, `fetch` and the JTAG, and the false paths of reset, switches, keys, LEDs and displays. Each crossing is bounded by the smallest period among the SoC clocks,

$$ b = \min_{r} T_r $$

and the name of the PLL nodes comes from the `clock_node_pattern` field of the family.

## 6. Compile and program

The `program` command uses the same generator before compiling (`quartus.generate` key of the `config.yaml`) and adds the compilation options.

| Option | Effect |
| :--- | :--- |
| `--seed N` | Placement seed, with the `HIGH PERFORMANCE EFFORT` mode fixed |
| `--generic NAME=VALUE` | Overrides a top generic for this compilation only |
| `--stop-after map\|fit\|sta` | Stops after the stage and does not program |
| `--compile-only` | Compiles and does not program |
| `--project-dir`, `--project-name` | Project written by `board generate` |

Compilation goes through a single Tcl script for all boards, and the estimator calibration uses the same script.

## 7. Uniqueness and equivalence

Three automatic checks protect the principle of section 1.

| Check | What it guarantees |
| :--- | :--- |
| Tools uniqueness test | Each kind of generated text has a single writer module |
| `check-boards` | A pin appears only in the `pins.yaml`, and chips and families are cited by name only |
| `board generate --check` | The project on disk is what the generator would write |

The equivalence of the generated DE0-CV project with the hand-written one is in [equivalencia-de0-cv.md](equivalencia-de0-cv.md).
