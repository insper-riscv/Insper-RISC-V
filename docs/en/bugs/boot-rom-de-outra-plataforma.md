# The board ran the boot ROM of another platform and the tests seemed to pass

## 1. Summary

The `sdram` platform kept, as its boot ROM image, a copy of the `internal-mem` image. The `riscv-tools` run flow does not recompile the boot ROM at each round. It writes into the bitstream whatever is in the project file. The board started running a boot ROM that clears addresses of the internal RAM, which the new platform no longer has.

| | |
| :--- | :--- |
| Symptom | All programs ended as PASS in about two seconds, and the programs with a golden failed the comparison |
| Cause | The project boot ROM image was the one of the other platform, with the mailbox and `go flag` addresses of the internal RAM |
| Fix | The project image is the platform boot ROM one, generated by the `program` command |
| Defense added | The host zeroes the mailbox before each test (see `docs/bugs` of Tools), so a wrong boot ROM no longer produces a false PASS |

## 2. The mechanism

The boot ROM of each platform does two things. It clears the words the host and the program share (mailbox, `go flag`, `tohost`, `fromhost`, `stdout` header) and it stays parked until the host triggers the `go flag`. The addresses of those words are inside the code.

| Platform | End of RAM | Mailbox |
| :--- | :--- | :--- |
| `internal-mem` | `0x00030000` | `0x0002FFFC` |
| `sdram` | `0x44000000` | `0x43FFFFFC` |

With the image of the other platform, the boot ROM wrote zeros to the old mailbox, which on the new platform is not memory, and left the SDRAM mailbox intact. The result of a test stayed there when the next test started, and the host read that PASS on the first access.

## 3. Why it went unnoticed

The tests without a golden (unit ones) all ended as PASS, because only the mailbox judges them. The tests with a golden showed the divergence, but in a batch that had been interrupted and resumed from the progress file, so the first dozens of results were from the interrupted batch. The sum of "everything passes in equal time" and "the golden disagrees with the PASS" raised the suspicion.

## 4. The fix

The platform `boot_rom_init.mif` image is generated from its `boot_rom.S` by the `riscv-tools program` command, which assembles the boot ROM, writes the file into the project, compiles and programs the board. The versioned file is now the platform one.

## 5. How to avoid it

Every platform has its own boot ROM image, and it must be regenerated whenever `boot_rom.S` or the memory map changes. The `run` command does not do this. A batch of tests must start from a clean progress file after any interruption.
